# 濾波候選的主機端評估（M6 P12b）：`tools/filter_eval.py` ＋ `tests/filter_lab*.c`

目的：在**真的 `km_engine` 邏輯**上，逐 frame 比較 `M6_PLAN.md` §6.4 的候選濾波器（F1–F5）：誤觸發、反轉延遲、靜止 σ、類比輸出的刻度跳動。
真實雜訊還沒量（P12a 的診斷映像要由主導者上板），所以**這份文件裡所有表都是合成雜訊的結果，是「初步」比較**，結論的可信度看 §5。

## 1. 它怎麼運作

```
深度路徑（真值，mm100）──▶ 感測器模型（km_depth_model 的反函數）──▶ 乾淨讀值
      ＋ 雜訊模型（白／慢／週期／突波／共模）──▶ 原始 12 位元樣本
      ──▶ [候選 F4 前置濾波] ──▶ km_scan（真的 km_scan.c，16 點滑動和）──▶ 和÷16 ──▶ [候選 F5 共模扣除]
      ──▶ 引擎（真的 km_engine.c 的副本，兩個濾波敘述改成呼叫「挑子」）──▶ 事件、f、g、深度
      ──▶ 類比路徑候選（F2，1 kHz）──▶ 8 位元刻度
```

- **引擎的副本** `tests/filter_lab_engine.c` 由 `tools/gen_filter_lab_engine.py` 從 `core/src/km_engine.c` **產生**（不手改）：公開函式改名 `lab_*`，
  主濾波 `f += (x−f)>>2` 與 RT 慢級 `g += …>>3` 兩行改成呼叫 `lab_hook_stage1/2`，RT 最小距離 20 改成變數（為了問「更小的距離會怎樣」）。
  F0（預設挑子）下，副本和真引擎**逐位元相同**：`tests/test_filter_traces.c` 在 5 種雜訊、5 把鍵（含 FIXED）上驗證事件、f、g、類比輸出完全一致。
  `km_engine.c` 一改（P12c），`gen_filter_lab_engine.py --check`（`filter_eval.py --self-test` 會跑）或這個等價測試就會失敗，提醒重新產生並看 diff。
- **真的 `km_scan`**：樣本打包成 DMA 字，推四個 phase 加 injected，跟 `noise_main.c`／`m5_main.c` 一樣取 `和>>4` 餵引擎。所以 16 點滑動和對雜訊顏色的影響是真的（§3 的重點）。
- **決定性**：固定種子；不用 libm（單元測試連結不需要 `-lm`）。
- **理想參照**：`lab_ideal_rapid/fixed` 是沒有濾波、沒有雜訊的完美偵測器（連續式 rapid trigger：比最淺點深 rt_down 就按下，比最深點淺 rt_up 就放開，頂部死區 0.20／0.10 mm）；
  引擎的事件與理想事件配對，差就是延遲（可為負：引擎的閾值有取整），配不上的是漏掉／多餘事件。**理想參照不含去抖動，所以延遲數字裡包含 0.34 ms（按下 8 frame）／0.26 ms（放開 6 frame）的去抖動**，這部分是所有候選共同的。

## 2. 雜訊模型（怎麼從現有文件定 σ）

`ENGINE_NOTES.md` 說感測雜訊是「±15 計數均勻、σ 8.7」，**加在引擎輸入端**（和÷16 之後），並且是白的；主濾波之後 σ 3.3，RT 慢級之後 σ 1.9。
我把這個叫 `legacy` 模型（`profile=legacy`，直接在引擎輸入端加 ±15 均勻雜訊），**重現了文件的數字**（f σ 3.28、g σ 1.86、60 s×4 鍵零誤觸發），所以工具與文件一致。

但真實的雜訊是出現在**原始樣本**，之後才過 km_scan 的 16 點平均。16 點平均本身是低通，它的輸出是強相關的：同樣的 f σ，原始雜訊小很多（白的話約 15 而不是 35），
而且後面的 IIR 對已經被平均過的訊號壓得比白雜訊少（g σ 約 2.7 而不是 1.9）。所以其他模型都**校準到同一個工作點：靜止時主濾波 f 的 σ ≈ 3.3 計數**（文件的工作點），只改「顏色」：

| 模型 | 原始雜訊 | 是什麼 |
|---|---|---|
| `legacy` | ±15 均勻加在引擎輸入 | 文件的假設（與 ENGINE_NOTES 的模擬相同） |
| `white` | 白，σ 14.8 | 原始樣本是白的 |
| `mixed` | 白 σ 13.6 ＋慢成分 σ 1.4（時間常數 17 ms） | 大部分白，一點點低頻 |
| `lowfreq` | 白 σ 4.2 ＋慢成分 σ 3.2（時間常數 86 ms） | 低頻為主（平均濾不掉） |
| `commonmode` | mixed ＋ 所有槽位共有的慢雜訊 σ 2.5 | 電源／參考電壓的共模 |
| `spiky` | mixed ＋ 一個 frame 長的突波，40 Hz、±48..96 | LED／USB 的孤立突波 |
| `tonal` | mixed ＋ 1 kHz 3 計數、50 Hz 2 計數 | 週期干擾 |

`scale=` 乘在所有成分上（scale 1.5 = 雜訊大 1.5 倍）。**這些模型的「σ 工作點」是文件的，不是我們量的**；P12a 量完要用實際 σ 重新定 `scale` 與顏色。

## 4. 怎麼解讀

**先講三個與候選無關的觀察，它們比候選的排名更重要：**

1. **噪音的顏色比 σ 更重要，而這還沒量。** 同樣的 f σ 3.3，`legacy`（白、加在引擎輸入）60 秒四把靜止鍵零誤觸發；`white`／`mixed`（原始樣本是白的／有一點慢成分，過 16 點平均）卻在 rt = 0.20 mm 有 10–13 次誤事件，
   最小安全距離從 0.20 mm 變成 0.25 mm（噪音 ×1.0），噪音 ×1.5 要 0.40 mm。原因：16 點平均的輸出本來就相關，後面的 IIR 壓不下去（g σ 約 2.7，不是 1.9）。
   所以 `ENGINE_NOTES.md` 的「0.20 mm 有 25 % 餘裕」只有在引擎輸入端真的是白雜訊、σ 8.7 時成立。實機到目前沒有誤觸發的回報，代表真實雜訊大概比這個工作點小（噪音 ×0.75 時 0.20 mm 就零誤觸發）——但這是推測，要 P12a 的數字。
2. **延遲裡有三分之一是去抖動，沒有任何候選碰它。** 0.3 m/s 時 F0 的按下延遲約 1.0 ms（mixed）／0.7 ms（legacy），其中 0.34 ms 是 8 個 frame 的去抖動；放開 1.2／0.9 ms 裡有 0.26 ms。濾波器能動的只是剩下的部分。
3. **「更快」和「更安靜」是兩個不同的候選，不是同一個。** F1B 快、不更安靜（反而更多誤事件）；F1C 更安靜、不更快（慢速時略慢）。

**候選逐一：**

| 候選 | 結果（合成） | 判斷 |
|---|---|---|
| **F1A**（只有 RT 慢級自適應） | 靜止時與 F0 完全相同（誤事件、σ 一樣）；快速動作時放開延遲少 0.1–0.2 ms，按下幾乎不變。動作很小 | 風險最低、收益最小；單獨做不值得，可併入 F1C |
| **F1B**（單級自適應取代兩級） | 延遲：0.3 m/s 按下／放開 −17 %／−22 %（mixed）、−32 %／−50 %（legacy）；但誤事件**更多**（white 18 vs 10，tonal 82 vs 53），安全距離不變。因為沒有第二級，方向守衛（f 與 g 的一致性檢查）形同虛設。FIXED 鍵沒有變快（閾值 12 計數時，0.3 m/s 的穩態落後約 8 計數，小於閾值，所以仍用小增益） | **低延遲選項**，要用換延遲換誤觸發；適合 `filter_mode = 1`，不當預設 |
| **F1C**（兩級都自適應） | 誤事件大幅減少：white 10→0、mixed 13→1、tonal 53→16、spiky 27→5、commonmode 202→138；f σ 3.3→2.9、g σ 2.7→2.5；噪音 ×1.5 的最小安全距離 0.40→0.30 mm。代價：慢速（≤ 0.1 m/s）延遲 +0.15–0.3 ms，≥ 0.3 m/s 與 F0 相當（±0.1 ms） | **安靜選項／預設候選**。意思是同樣的誤觸發率下，噪音 ×1.5 時可以把 rt 距離從 0.40 減到 0.30 mm（約 25 %；噪音 ×1.0 時沒有差，仍是 0.25 mm）。方向對 §6.4 目標 2(b)，但離 0.15 mm 還遠 |
| **F4M**（3 點中值） | **更糟**：white 35 vs 10、tonal 95 vs 53。中值濾波讓相鄰樣本相關，16 點平均的降噪變差。只對「孤立的 1 frame 突波」有效（`spikeonly` 模型，f σ 1.05→0.14）。2 frame 以上的突波中值也擋不住 | 除非 P12a 真的看到孤立 1 frame 突波，否則**不做** |
| **F4C**（限幅 ±45） | 除了 spiky（27→19）外與 F0 相同 | 同上；要先看到突波 |
| **F5**（共模扣除，32 個參考鍵） | commonmode：202→11；其他模型中性（white 10→4 可能是隨機）；沒有共模時對 σ 幾乎無害（+1–2 %） | **取決於 P12a 的共模占比**。占比大（情境 D 的 `common` > 0.3）就值得，否則不做 |
| **F3**（每鍵雜訊底限） | 安靜的鍵可用更小的距離：F0 噪音 ×0.5 時 0.12 mm 零誤事件，×0.75 時 0.20 mm，×1.0 時 0.25 mm | 能降多少只取決於各鍵 σ 差多少（P12a 情境 A 的 worst/median）。差 ≥ 1.5 倍才值得做 |
| **F2**（類比路徑，F2 表） | 引擎現行 `km_engine_depth`（f、整數計數）靜止 σ 1.3–1.4 刻度、每秒變 750 次（1 kHz 取樣上限 1000）——搖桿會一直跳。IIR 1/4 ＋遲滯：σ 0.5–0.7 刻度、每秒變 90 次，代價是 90 % 上升時間 7.5 ms。要在 mixed 雜訊下到 ≤ 0.5 刻度，推測需要更長的平滑（約 1/8、15 ms 級）或更大的遲滯（這兩種沒評估） | **一定做**（P4 需要），平滑等級給 `PAD.smooth`。一個計數對應約 0.6–0.75 刻度（頂部斜率），所以低於 0.5 刻度需要子計數內插（工具已用） |
| F6 漂移、F7 取樣端 | **這個工具評估不了**：漂移需要實測的暖機資料，F7 需要硬體 | 看 P12a 情境 E；F7 要你同意 |

## 5. 這些結果能信多少（誠實的限制）

- **全是合成的。** 雜訊的 σ 來自文件的工作點，顏色是假設。lowfreq 模型下所有候選都幫不上忙（4–8 次誤事件，各候選差不多）；如果真實雜訊像這樣，要靠別的方法（漂移追蹤、更大的距離）。**P12a 的數字出來之前，不要根據這張表改引擎。**
- 靜止時間只有 15–60 秒 × 4 把靜止鍵（約 1–4 分鐘鍵等效），不是 §6.4 驗收要求的「1 小時以上零誤觸發」。表是篩選用；要最後驗收用 `filter_lab_cli quiet seconds=3600`（單次約 1 分鐘多核並行）。
- 手指微晃（wobble）是 8 Hz、振幅 ±0.15 × rt 的正弦，振幅是我隨便定的；括號裡的數字只看相對大小。
- 自適應增益的閾值（12／32 計數）還沒調；`t1=`／`t2=` 可掃描。閾值要跟著真實 σ 走。
- 理想參照不含去抖動，也不含 bottom dead zone、continuous = 0 的規則；延遲是「引擎事件 − 理想事件」，不是「手指到電腦」。
- 感測器斜率用最陡的鍵（跨度 1000 計數）；最緩的鍵（1365）同樣的計數雜訊對應更小的深度雜訊。
- 類比路徑的統計是 1 kHz 取樣；IIR 狀態用 double（實作時要換成整數／Q 格式，有捨入的差）。
- 事件的 p95 來自 ≤ 100 次反轉（5 seed × 20 週期），夠看趨勢、不夠看尾巴。
- 主機 `bench` 的 ns／frame 包含雜訊產生與 km_scan，不是引擎週期數；它只說明各候選相對成本不大（F1C 比 F0 多約 25 % 的整條流程時間），**CPU 成本以計畫書 §6.7 的估算為準**，P12c 要用 `eng_max` 實機驗證。

## 6. 給 P12c 的建議（量到數字之前的版本）

1. **一定做：F2 類比路徑**（`km_engine_analog()`）：1 kHz、子計數內插的 IIR ＋ 遲滯，平滑等級由 `PAD.smooth` 選（約 1/2、1/4、1/8、1/16）。它跟引擎的判定邏輯無關，風險小，P4（手把）需要它。
2. **預設候選：F1C**（兩級自適應增益），放進 `DEVICE.filter_mode`：0 = 現行 F0、1 = 低延遲（F1B）、2 = 安靜（F1C）。實機 A/B（L6-S1）決定預設。閾值（12／32）用 P12a 的 σ 重新定。
3. **有條件才做：** F5 共模扣除（P12a 情境 D 的共模占比 > 0.3）；F3 每鍵底限（情境 A 的 worst/median ≥ 1.5）；F4C／F4M 突波抑制（看到孤立突波才做，中值法不建議）。
4. **不做：** F4M 當預設；F1A 單獨做。
5. **動引擎前**：用真實 σ 與顏色重跑 `filter_eval.py --matrix`，確認排名沒變；`test_engine*` 的數字若變要逐條說明；`tools/mutate_engine.py` 要擴充；重做 `ENGINE_NOTES.md` 的雜訊推導（§1 的觀察 1 說明舊推導的前提）。

## 7. 怎麼用

```
python firmware/tools/filter_eval.py --self-test                 # 建置、與引擎同步檢查、基本行為（約 1 分鐘）
python firmware/tools/filter_eval.py --matrix [--quick]          # 上面 §3 的表（完整約 4 分鐘，--quick 約 1 分鐘）
python firmware/tools/filter_eval.py --trace noise_data/A_idle_all [檔案或資料夾...] [--mode rapid|fixed] [--rt 20]
python firmware/tools/filter_eval.py --bench
filter_lab quiet|latency|step|trace|bench key=value ...          # filter_eval.py 在暫存目錄建的 CLI（建置指令見它的 build()；參數見 tools/filter_lab_cli.c 開頭）
python firmware/tools/gen_filter_lab_engine.py [--check]        # 重新產生／檢查引擎副本（km_engine.c 改過就要跑）
```

**載入真實量測**（`tools/magger60_noise.py` 存的 `.kmtr`，格式見 `core/NOISE_NOTES.md`）：`--trace` 逐個檔案、逐個候選（F0…F5）餵進引擎（欄位 c 對應 key c，槽位用檔頭的），
印出各欄的 f／g σ、類比輸出 σ 與刻度跳動、事件數。靜止量測（情境 A、C、D）事件數應為 0，否則就是真實的誤觸發；按著鍵的量測（情境 B）看類比輸出的 σ。
沒有真值深度，所以真實軌跡不算延遲；延遲只在合成路徑上算。真實軌跡的 `*.kmtr` 很小（4 欄 × 4096 frame = 32 KB）可以放進 `tests/traces/`（只放我們自己量的資料）。
真實的 σ 要拿去調 `profile`／`scale`：`noise_data` 報告的 `sigma` 和 `color`（顏色係數）對應本文 §2 的模型參數：白的部分 ≈ `sigma`，顏色係數 ≈ 1 表示全白、≥ 2 表示低頻為主。
