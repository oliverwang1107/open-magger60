# Bad Apple 動畫：格式、工具、亮度與著作權（M6 工作包 P7b）

這份文件說明「把一段黑白剪影影片變成 61 顆燈上的動畫」整條鏈：**轉檔工具 → 壓縮資料 → 韌體解碼器 → 燈光層**。
韌體只收**解碼器**（`firmware/core/src/km_anim.c`）和**轉檔工具**（`tools/badapple_convert.py`）；
影片、音樂和轉出來的資料都是別人的著作或由它們衍生，**永遠不進 repo**（第 7 節）。

## 1. 白話：這是什麼、能看到什麼

61 顆燈排成 5 排（14／14／13／12／8 顆），可以當成約 15 × 5 格的超低解析度螢幕。
Bad Apple 縮到這個尺寸只剩大塊的明暗：看得到人影的移動和場景切換，**看不到細節**（臉、文字）。
所以它是「跟著音樂的光影秀」。轉檔工具會先產生預覽 GIF，確認好看再燒。

鏈條：

```
你的影片檔 ──badapple_convert.py──▶ badapple.kman（壓縮資料）──▶ 編進韌體映像（const 陣列）
                                                                      │
                          km_anim_tick() 每次輸出 61 個灰階值 ◀──────┘
                                      │
                    P6c 燈光層的「外部影格」──▶ 亮度縮放 ──▶ 三道硬限制 ──▶ 燈
```

## 2. 資料格式 KMAN v1（精確規格在 `km_anim.h` 的註解）

- 標頭 20 位元組：魔術字 `KMAN`、版本、燈數 61、每格位元數（1／2／4）、fps（1..60）、影格數、
  關鍵影格間隔 K、旗標（bit0 = 建議循環）、兩個 Exp-Golomb 階數（變化個數、間隔）、群組數、資料長度。
- 調色盤：每個樣本值對應的灰階（0..255，嚴格遞增）。這裡面已經含 gamma（樣本是「感知」階，燈是線性的）。
- 索引：每個群組（K 個影格）在資料裡的起點，u16；用來快速跳到關鍵影格。
- 資料：每個群組先 1 個**關鍵影格**（61 格 × 位元數，原樣存），後面 K−1 個**差分影格**：
  「有幾格變了」＋「每格：跳過幾格、新值」。1 位元時新值不必存（翻轉）。這就是設計文件 §5.5 說的
  「關鍵影格＋差分遊程」。數字用 Exp-Golomb 碼，**階數由轉檔工具對整段資料試 25 種組合挑最小的**。
  群組結尾補 0 到整位元組。
- 結尾 4 位元組 CRC-32。
- 長度上限：資料 ≤ 65535 位元組、群組 ≤ 1024、影格 ≤ 65535。超過時工具直接拒絕（不會悄悄截斷）。

**嚴格驗證**（韌體每次解碼都檢查，違反就進 `ERROR` 狀態、輸出停止更新，不會當機）：
標頭每個欄位範圍和保留位元、總長度必須剛好吻合、調色盤遞增、索引遞增且每群組至少放得下一個關鍵影格；
解碼時每次讀取都被限制在「自己這個群組」裡，變化的格子不能超過第 61 格，「沒有改變任何東西的變化」不合法
（編碼唯一），群組必須剛好在索引指的位置結束且補位元為 0。另外有分段式的完整檢查（CRC＋逐影格解碼），
可以在主迴圈裡一次做一點點。

## 3. 大小（要老實說：下面是「合成片段」的估計，不是 Bad Apple 的實測）

我沒有（也不應該取得）Bad Apple 的影片，所以數字來自 `python tools/badapple_convert.py --synth-report`：
一段**自己編的** 3:39（219 秒）片段——白底上 2～4 個會移動的深色橢圓，每 6 秒換一次場景，
轉成預設的反相、置中裁切。真正的 Bad Apple 動得比較多，**實際大小很可能是下表的 1.5～3 倍**；
真正的數字要你拿自己的影片跑工具，它會印出來（`--stats`）。

| fps | 1 位元（黑白） | 2 位元（4 階灰） | 4 位元（16 階灰） | 平均每影格變化格數（1／2／4 位元） |
|---|---|---|---|---|
| 10 | 4.2 KB | 11.2 KB | 25.4 KB | 2.1 ／ 5.4 ／ 11.5 |
| 15 | 5.0 KB | 13.2 KB | 34.9 KB | 1.4 ／ 3.7 ／ 9.9 |
| 30 | 6.7 KB | 16.9 KB | 55.2 KB | 0.7 ／ 1.9 ／ 6.9 |

（KB = 1000 位元組；位元組數：4231／11241／25415、4969／13168／34860、6729／16915／55175；K = 30。）

對照：未壓縮（每影格都存，1 位元 8 位元組、2 位元 16、4 位元 31）15 fps 是 26.3 KB／52.6 KB／101.8 KB。
壓縮倍數在這個合成片段上是 3～8 倍；設計文件原先估 2～6 倍。

最壞情形（每一格每個影格都變，等於雜訊）：1 位元約每影格 9 位元組（15 fps 約 30 KB），2 位元約 24（約 80 KB），
4 位元約 40（約 130 KB）。2 位元和 4 位元的最壞情形會超過格式上限 64 KB，工具會拒絕。
韌體映像給資料的預算約 **40 KB**（`M6_PLAN.md` §5.5）：`--max-bytes` 預設 40000，超過就報錯，
請降 fps 或位元數。建議起點：**15 fps、2 位元**；不夠就 10 fps，或 1 位元。

## 4. 播放時鐘與「開始」命令（與 `M6_PLAN.md` §5.4 的方案 B 一致）

鍵盤用自己的計時（晶體 ±20 ppm，219 秒偏差 < 5 ms）。PC 只在**開始音樂的那一刻**告訴鍵盤一次：

| 欄位 | 意義 |
|---|---|
| `flags` bit0 | 循環播放 |
| `flags` bit1 | 影格間內插（每個影格之間分 16 階線性混合；15 fps 的資料看起來平順很多，代價是每個顯示 frame 多 61 次乘法） |
| `offset_ms`（有號 32 位元） | 收到命令的此刻，音樂已經播到第幾毫秒。**負數** = 音樂還有這麼久才開始（鍵盤先顯示第一個影格等著）。 |

另外兩個動作：**停止**（回到原本的燈效）、**狀態**（回報 IDLE／PLAYING／DONE／ERROR 和目前影格）。
同一個「開始」命令在播放中再送一次 = **重新對時**（時鐘移動、解碼器不重來）。

這是給 P7a（串流命令 `0xC7` 的作者）和 P8（協定）的**建議格式**：負載 `[op][flags u8][offset_ms i32 LE]`，
op 建議 `0x10` 開始、`0x11` 停止、`0x12` 狀態；實際編號和包裝由 P7a／P8 決定，解碼器的 API（第 6 節）
不依賴它。也可以由按鍵觸發（`offset_ms = 0`）。PC 端的延遲補償（USB 約 1～2 ms ＋ 主機排程抖動 ±10 ms）
由 PC 工具用 `offset_ms` 微調。

時間精度：影格 f 從 `f × 1000 / fps` 毫秒開始，用 1/1000 影格為單位的整數算，**不累積誤差**。
32 位元毫秒時鐘繞回（49.7 天）沒問題，只用差值；連續播放超過 49.7 天會有一次相位跳動，可忽略。

## 5. 亮度、電流，以及為什麼預設「反相」

燈光有三道**編譯期**硬限制（`km_led.h`，`LED_NOTES.md`）：每通道 ≤ 140、單顆三通道總和 ≤ 280、
全部通道值總和 ≤ 3060（模型電流 180 mA，**每通道 15 mA 是假設值，沒量過**）。
動畫輸出的灰階是「限制之前」的亮度，之後照樣被縮放與限制；**動畫、串流不會放寬任何一道**。

| 畫面（白色燈） | 亮燈數 | 整體縮放 | 亮的那顆實際每通道值 |
|---|---|---|---|
| 全白 | 61 | 17.9 % | 約 17 |
| 原版（白底黑人，約 70 % 白） | 43 | 25 % | 約 24（約 9 %） |
| **反相**（黑底白人，約 25 %） | 15 | 73 % | 約 68（約 27 %） |

結論：白底的原版在 180 mA 模型下**很暗**，所以工具**預設反相**（人影亮、背景暗）。想要原版用 `--no-invert`。
`--stats` 會用同一個模型算出你的片段的平均與最壞縮放比和電流。（模型順序同 `km_led.h`：先每通道上限、再單顆上限、
最後總電流；預覽 `--preview-limited` 也用它。）

調色盤小提醒：白色燈的單顆上限是 280／3 ≈ 93，所以**灰階 93 以上的階在白光下都被壓成一樣**。
若燈色是白色，用 `--max-level 93`，讓階數落在看得見的範圍（4 位元時最暗的幾階會被推開 1 級，工具會提示）；
若燈色是單一顏色（例如只用綠色通道），上限是 140。預設 255 保留最大彈性，實際效果以 `--stats` 為準。

是否提高 `KM_LED_BUDGET_MA`（編譯期常數，需要你同意）：**先用 USB 電流計量真實電流再決定**，
預設仍是 180 mA（裝置宣告 300 mA，MCU＋USB＋感測器本身約 80～120 mA）。

## 6. 工具與 API

### 轉檔工具

```
python tools/badapple_convert.py 你的影片.mp4 -o badapple.kman --preview badapple.gif --stats
python tools/badapple_convert.py 影格資料夾/ --src-fps 30 --fps 15 --bits 2 --fit crop
python tools/badapple_convert.py --check badapple.kman        # 照韌體的規則嚴格檢查
python tools/badapple_convert.py --self-test                    # 不需要影片
```

- 需要：Python 3、numpy、Pillow（這台機器已有；沒有就 `pip install numpy pillow`）。**影片檔另外需要 ffmpeg**
  （這台在 `C:\ffmpeg\bin`，已在 PATH）；沒有 ffmpeg 就先把影片匯出成圖片資料夾再給資料夾。
- 取樣：每顆燈取以燈為中心 1 × 1 鍵寬的方格，在**線性光**下做面積平均（先 gamma 2.2 還原），再量化。
- 版面（`--fit`）：`crop`（預設，取中央橫條；`--crop-y` 可上下移、`--zoom` 放大）、`stretch`（壓扁）、
  `letterbox`（留黑邊，有效解析度掉到約 7 × 5）。燈區長寬比 3:1，Bad Apple 是 4:3，所以一定要取捨。
- 量化：`--bits 1|2|4`；1 位元用 `--threshold`；`--dither none|bayer|fs`（有序／誤差擴散，會增加資料量）；
  `--hysteresis`（邊緣閃爍抑制）；`--invert`（預設）／`--no-invert`。
- 預覽 GIF 是從**剛寫出的檔案解碼**出來的，看到的就是鍵盤會播的內容（GIF 以 10 ms 為單位，工具會平均分配進位）。
- `--c-array 檔.c --symbol 名稱`：輸出可編進映像的 const 陣列。
- `--synth-report`：第 3 節的合成表。

### 韌體 API（`km_anim.h`，純 C、無硬體、無配置）

```c
km_anim_info_t info;
if (km_anim_parse(clip, clip_len, &info) != KM_ANIM_OK) { /* 資料不對：不要播 */ }
km_anim_t anim;  km_anim_init(&anim, &info);
km_anim_start(&anim, now_ms, offset_ms, KM_ANIM_PLAY_LOOP | KM_ANIM_PLAY_BLEND);
...
uint8_t frame[61];                        /* 燈的順序 = km_led 的燈編號 0..60（蛇形） */
if (km_anim_tick(&anim, now_ms, frame)) { /* 新的一格：交給 P6c 的外部影格層 */ }
if (km_anim_state(&anim) != KM_ANIM_PLAYING) { /* DONE 或 ERROR：燈光層回到原本的效果 */ }
```

- 每次 `km_anim_tick` 的成本有上限：最多解 8 個影格，最壞約 640 格（`km_anim_last_work()` 可讀），
  影格沒變時幾乎是零。停頓之後輸出會落後時鐘幾次呼叫、再追上；時鐘倒退或跳很遠會改跳關鍵影格。
- `parse` 約幾百個週期（只看標頭、調色盤、索引）。完整檢查用 `km_anim_verify_begin/step`
  （每步 256 位元組 CRC 或一個影格），在主迴圈每圈做一步；`km_anim_validate()` 是一次做完（只給主機與測試）。
- RAM：`km_anim_t` 約 200 位元組。解碼器輸出的是灰階（0..255）；上色（白、單色）是燈光層的事。

- Bad Apple 的**影片與音樂是第三方作品**。repo 只放轉檔工具和格式規格；轉出的 `.kman`、預覽 GIF、
  由它產生的 C 陣列都不進 repo。音樂由 PC 播放，不由鍵盤送出。

## 8. 實機上要測什麼（L6-6）

1. **對時**：PC 同時開始音樂與送開始命令，看燈與音樂的同步；試 `offset_ms` 微調；整首 219 秒後有沒有漂移（預期 < 5 ms）。
2. **亮度與電流**：反相與原版各播一次，用 USB 電流計記錄；確認三道限制沒有被越過、白光下最亮灰階被壓成 93 以內。
   這同時校正 `KM_LED_MA_PER_CHANNEL` 的假設值（15 mA）。
3. **打字不受影響**：播放中打字、快速觸發照常；`pass_cycles_max`（M6 scope 計數器）在影格邊界那圈和關鍵影格那圈
   沒有明顯增加（估計 < 1k 週期）。
4. **完整檢查耗時**：在主迴圈逐步做 `km_anim_verify_step`，確認掃描率不降。
5. **循環與停止**：循環接縫是否順（最後一格接第一格）；停止後燈光回到原本的效果；拔掉 PC 工具後動畫照播到結束。
6. **破壞測試**（可選，在獨立映像）：故意改壞映像裡的資料一個位元，確認進 `ERROR`、燈回原效果、鍵盤不受影響。
7. 內插（BLEND）開與關的觀感比較，10／15 fps 各一次。
