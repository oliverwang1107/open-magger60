# Light frame stream (command 0xC7), version 1

A PC tool sends complete frames of the 61 lights to the keyboard in real time; the keyboard shows them instead of its normal
effect for as long as the stream lives. It runs on the vendor-class HID interface (IF1, 64-byte reports, report ID 0) next to
cmd 3, the scope command 0xC5 and the configuration protocol 0xC6, which are untouched. The device side is
`firmware/hid/src/km_stream.c` (hardware independent, tested on the host in `firmware/tests/test_stream.c`), the host side is
`tools/magger60_stream.py`. The packets in section 8 are written out byte by byte in `firmware/tests/golden/stream_vectors.h`,
generated by the independent keyboard model inside the host tool (`--gen-vectors`) and replayed against the C code.

Everything here is original to this project. It must never be sent to the stock firmware: the host tool checks that the cmd 3
build string carries `KMFW` before it sends a single 0xC7 packet. A keyboard that does not know the command answers `"unknw"`.

## 1. Properties (what the design guarantees)

* **One-directional.** Frames go to the keyboard. Only packets that ask (flag `ACK_REQ`) and the control packets (START, STOP,
  KEEPALIVE) are answered. A frame chunk without `ACK_REQ` gets no reply, so a host that never reads cannot make the keyboard
  queue anything.
* **Self-ending.** No valid packet of the session for `timeout` ms (default 500, 100..5000) and the keyboard returns to its own
  effect by itself. A crashed or unplugged host, a sleeping PC, a closed lid: the lights come back within half a second.
  32 malformed packets in a row also end the session.
* **Never half a frame.** A frame is shown only when all 61 lights of one frame number have arrived; it is assembled in a
  separate buffer and swapped in as a whole.
* **Bounded.** One request is one 64-byte report, at most 48 pixel bytes copied, no loop over anything the host controls, no wait.
  It runs in the main loop (same context as cmd 3 / 0xC5 / 0xC6), never in the scan interrupt, and touches no flash and no
  register. The key path and the USB endpoint cannot be blocked by it.
* **No new power.** The frame goes through the light core's three hard limits (per channel 140, per light 280, total current model)
  like every other effect. Nothing in the stream can raise them.
* **Strict.** Every field is range-checked before anything is changed; a refused packet changes neither the frame, the sequence
  number nor the time-out.

## 2. Frame (packet) layout

A request is an ordinary `'U'` packet (see `km_hid.h`):

```
[0]    0x55            header 'U'
[1]    0xC7            command (KM_CMD_STREAM)
[2]    0x00            XOR key, must be 0 (a masked request is refused: BAD_ARG)
[3]    checksum        (len + off0 + off1 + off2 + sum(data[0..len-1])) & 0xFF
[4]    len             number of data bytes, 3..56
[5..6] seq             LE16 sequence number (the "offset" field of the frame)
[7]    0x00            must be 0 (a non-zero byte is refused: BAD_ARG)
[8..]  data            len bytes, then zero padding to 64 bytes
```

Every request starts with the same three data bytes:

| data | meaning |
|---|---|
| `d[0]` | op: 1 START, 2 FRAME, 3 STOP, 4 KEEPALIVE (0x10..0x1F reserved for the animation player) |
| `d[1]` | session id, 1..255, chosen by the host (0 is never valid) |
| `d[2]` | flags: bit 0 `ACK_REQ` (please answer this packet); every other bit must be 0 |

Fewer than 3 data bytes: not answered at all (counted as rejected).

### START (op 1), len = 8

| data | meaning |
|---|---|
| `d[3]` | protocol version, must be 1 |
| `d[4]` | pixel format: 0 RGB8 (3 bytes per light), 1 GRAY8 (1 byte per light, shown as r = g = b) |
| `d[5..6]` | time-out in ms, LE16; 0 = default 500; otherwise 100..5000 |
| `d[7]` | reserved, 0 |

`seq` of the START is the **base**: the first packet that follows must be newer than it (normally base + 1). START opens a
new session (also while one is open: the old one is replaced), clears the statistics and the frame state, and shows nothing
yet: state OPEN. Refused with UNAVAILABLE while the light core vetoes streams (light fault, lights off).

### FRAME (op 2), len = 6 + count * bpp

| data | meaning |
|---|---|
| `d[3]` | frame number (8 bit, wrapping); all chunks of one frame carry the same number |
| `d[4]` | first light of this chunk, 0..60 |
| `d[5]` | number of lights in this chunk, 1..(61 - first) |
| `d[6..]` | pixels: `count * 3` bytes `r g b` (RGB8) or `count` bytes (GRAY8) |

Light `i` is light `i` of `km_led.h` (wiring order, snake: row 0 = lights 0..13 left to right, row 1 = 14..27 right to left, row 2 =
28..40, row 3 = 41..52 right to left, row 4 = 53..60; positions in `km_led_x8()`). `len` must be exactly `6 + count * bpp`.
One packet carries at most 16 RGB lights or 50 gray lights, so a whole frame is **4 RGB packets (16, 16, 16, 13 lights) or 2 gray
packets (50, 11)**. Chunks may arrive in any order and may overlap; the frame is complete when every light was covered.

### STOP (op 3), len = 3 and KEEPALIVE (op 4), len = 3

STOP closes the session at once (the session id must match; the counters stay readable). KEEPALIVE keeps the session alive when
nothing else is sent (a static colour needs one every `timeout / 3` or so) and is always answered: it is also the "status" query.

## 3. Reply (only to START, STOP, KEEPALIVE, refused control packets, and packets with `ACK_REQ`)

Standard response frame: `[0] = 0xAA`, `[1] = 0xC7`, `[4] = 22`, `[5..6]` = the `seq` of the request, `[7] = 0`, data from `[8]`.

| data | meaning |
|---|---|
| `d[0]` | op of the request |
| `d[1]` | status: 0 OK, 1 UNKNOWN_OP, 2 BAD_LENGTH, 3 BAD_ARG, 4 SESSION, 5 STALE, 6 UNAVAILABLE |
| `d[2]` | session id now open (0 = none) |
| `d[3]` | state: 0 IDLE, 1 OPEN (session, no complete frame yet), 2 LIVE (a complete frame is on show) |
| `d[4..5]` | newest accepted sequence number (cumulative acknowledgement), LE16; kept when the session ends |
| `d[6]` | frame number of the frame on show |
| `d[7]` | window: 16 |
| `d[8..9]` | `committed`: complete frames made visible (wraps) |
| `d[10..11]` | `dropped`: frames abandoned incomplete because a newer one began |
| `d[12..13]` | `lost`: packets missing in the sequence (gaps), saturating |
| `d[14..15]` | `stale`: repeated, late or reordered packets ignored, saturating |
| `d[16..17]` | `rejected`: malformed or wrong-session packets, saturating |
| `d[18]` | protocol version (1) |
| `d[19]` | supported pixel formats as a bit mask (3 = RGB8 and GRAY8) |
| `d[20..21]` | time-out in force, ms, LE16 |

A refused control packet (bad length, bad argument, no such session, unknown op) is answered with the error status. A refused
**frame chunk** is answered only if it carried `ACK_REQ`. Acknowledgements (`ACK_REQ`) are answered at most once per 2 ms; the answers
to control packets are never held back. The status SESSION with state IDLE is how the host learns that the keyboard has ended the
stream (time-out, power, another tool): it starts again with a new START.

## 4. Sequence numbers, loss, duplicates and reordering

`seq` is a 16-bit counter the host increments for **every** packet of the session (START carries the base). The keyboard keeps the
newest accepted number `last`; for a valid packet with number `n`, `diff = (n - last) mod 65536`:

* `diff == 0` or `diff >= 32768`: **repeated or older**: ignored, counted as `stale`, answered STALE (if an answer was due). It does not keep
  the session alive.
* otherwise: accepted; `lost += diff - 1`, `last = n`. The packet is applied and the session's time-out restarts.

Frame numbers use the same idea with 8 bits: the number of the frame under assembly is `cur`; a chunk with `(f - cur) mod 256` in
1..127 is **newer** (the incomplete older frame is abandoned, `dropped++`, a fresh frame begins), 0 is the same frame, 128..255 is **older**
(ignored, `stale++`). A chunk of a frame that is already on show is ignored too. After START the first frame number is accepted
whatever it is.

Consequences: a lost chunk costs exactly its frame (the previous frame stays on show); a chunk that arrives late costs nothing; a
duplicate costs nothing. A frame is replaced only by a complete newer one, never partly.

## 5. Flow control and rate limits

* The host numbers its packets and sets `ACK_REQ` on every 8th. The reply names the newest accepted number; the host keeps
  **at most 16 packets (the window) unanswered** (`seq - d[4..5]`), and **skips a frame instead of queueing it** when the window is full.
  A silent keyboard is asked with a KEEPALIVE (always answered); the host gives up after three tries.
* Frame rate: the lights refresh at most every 20 ms (50 fps, `KM_LED_FRAME_MS_ANIM`). More frames are accepted (the latest complete one
  wins) but cannot be seen. Recommended: 30 fps, at most 50. The host tool defaults to 30.
* The keyboard answers at most one `ACK_REQ` per 2 ms. 32 consecutive malformed packets end the session.
* Reply traffic is the only IN traffic of the stream: with `ACK_REQ` on every 8th packet and 4 packets per RGB frame that is about
  one 64-byte reply per two frames (about 15 per second at 30 fps).

## 6. Numbers

The vendor interface is an interrupt IN/OUT pair, 64-byte reports, `bInterval` 4 at high speed = 1 ms
(`km_usb_ids.h`): at most 1000 packets per second each way, 56 data bytes each.

| frame | packets | 30 fps | 50 fps | share of 1000 pkt/s |
|---|---|---|---|---|
| RGB8, 61 lights (183 bytes) | 4 | 120 pkt/s | 200 pkt/s | 12 % / 20 % |
| GRAY8, 61 lights (61 bytes) | 2 | 60 pkt/s | 100 pkt/s | 6 % / 10 % |

Theoretical maximum 250 RGB frames/s or 500 gray frames/s, but the lights show 50 fps at most. So **30 fps RGB is comfortable,
50 fps RGB fits** (it needs a host that can write 200 reports per second with steady timing, which hidapi on Windows normally does;
this is to be measured on the keyboard). Latency from the host's write to the light: USB 1 ms + at most one main-loop pass + up to 20 ms
for the next light frame.

## 7. What the light core (P6c) consumes

`km_stream.h`, all from the main loop:

```c
km_stream_tick(&s, now_ms);                         /* once per pass, before the USB poll: clock + time-out */
if (km_stream_active(&s)) {                         /* state LIVE */
    const uint8_t *rgb = km_stream_frame(&s);       /* 183 bytes, light 0..60, r g b: copy it at once */
    uint32_t serial = km_stream_serial(&s);         /* changes with every new frame */
} /* else: normal effect */
km_stream_set_enabled(&s, false);                   /* veto: closes a session, START answered UNAVAILABLE */
km_vendor_set_stream(&s);                           /* registers 0xC7 with km_vendor_handle */
```

The pixel values are "before brightness and limits"; the core applies its three limits to them like to any effect. The wire order
(GRB) is the core's business. `KM_STREAM_LIGHTS` must equal `KM_LED_COUNT` (assert it in the core). Memory: `sizeof(km_stream_t)` about 460 bytes
of RAM, about 1.3 KB of code.

## 8. Worked example

START, session 7, base 65530, RGB, 600 ms:

```
55 c7 00 64 08 fa ff 00 | 01 07 00 01 00 58 02 00     (op 1, session 7, flags 0, version 1, fmt 0, timeout 0x0258, reserved 0)
```
Reply (OPEN): `aa c7 00 .. 16 fa ff 00 | 01 00 07 01 fa ff 00 10 00 ...`. First FRAME chunk: `seq` 65531, frame 1, lights 0..15: `d = 02 07 00 01 00 10 <48 bytes>`.
The complete scripted conversation (about 30 steps with replies, state, frame hash) is in `firmware/tests/golden/stream_vectors.h`.

## 9. Host procedure (what `magger60_stream.py` does)

1. cmd 3: build string must carry `KMFW`. KEEPALIVE with an unused session: the reply must be a 22-byte 0xC7 reply with version 1
   (an `"unknw"` answer means the firmware has no stream).
2. START with a random session id and a random sequence base; wait for the reply (resend after 100 ms, three tries).
3. Per frame: poll the replies, restart if a reply says IDLE or another session, skip the frame if the window is full, otherwise send the chunks
   with increasing `seq` and the next frame number, `ACK_REQ` on every 8th packet.
4. For a static picture: one frame, then KEEPALIVE every `timeout / 3`.
5. At the end (also on Ctrl+C): STOP. If the tool is killed instead, the keyboard ends the stream by itself after the time-out.

## 10. For the configuration protocol (P8) to reference

* Command 0xC7 exists from firmware that registered it with `km_vendor_set_stream()`; a feature bit in GET_INFO (suggested: the next free bit) can
  announce it. Until then the host probes with a KEEPALIVE.
* A `DEVICE_STATUS` may expose the statistics (`committed`, `dropped`, `lost`, `stale`, `rejected`, state) read from `km_stream_stats()` / `km_stream_state()`.
* The light core's `EXTERNAL` effect (7..9 in the plan) is "the stream is active"; no config byte is needed to start or stop a stream.
* Reserved here for the animation player (P7b/P10): ops 0x10..0x1F on 0xC7 (start with a music offset, stop, status).
